# CHOGPIT self-review and remediation — **not** an independent audit

> **HISTORICAL SCOPE NOTICE:** This 17 October self-review assessed the earlier signed-wallet, no-minimum withdrawal draft. The user subsequently chose passkey accounts, automatic 50-CHOG payouts, carry across funded epochs and a controlled final settlement. The older claim findings/tests below do **not** audit that replacement. Consult `REWARD_LAUNCH_READINESS.md` and `CLAIM_REVIEW_HANDOFF.md` for the current design; public payouts remain NO-GO.

**Date:** 17 October 2026  
**Reviewer:** project team/assistant reviewing its own implementation  
**Release decision:** **NO-GO for real $CHOG awards, mainnet funding, or gas-sponsored public claims.** The shooter remains a playable **preview**, not a finished prize campaign. No owner or sponsor wallet was connected; no private key was requested; no contract was deployed or funded.

This document records targeted code inspection, negative-case tests and repairs in the current workspace. It is **not** a legal opinion, independent security audit, proof of fair eligibility, or authority to turn on payouts. The owner reports having 1,000 CHOG in a wallet and written rules approved, but neither wallet holdings nor the rules/reviewer sign-off were supplied for verification. The pool is **not** in a vault.

## Scope and method

Reviewed `server.mjs`, `live-rooms.mjs`, `reward-preview.mjs`, the arena-edit and wallet UI, the isolated local-test claim journal/proof builder, the un-deployed Solidity vault draft and local mock-chain tests. Traced how server-checked box observations are kept separate from actual claim events. Tried adversarial API inputs for signed arena edits, fake raids, forwarded-IP rotation and WebSocket origins; checked room-creation concurrency and oversized Merkle/gas inputs. Examined dependency advisories. Tests used temporary local files, disposable wallets and mock tokens **only**. This was not a formal audit, full fuzz campaign, external penetration test, testnet deployment, or live mainnet claim.

## Findings fixed in this review

| ID / severity | Finding and impact before the fix | Change and verification |
|---|---|---|
| SR-01 **High — NFT arena integrity** | The owner's personal-sign challenge named an arena and nonce but **not the proposed traps**. A signed, still-valid challenge could have been submitted with a different valid trap layout. | Challenge is now a rate-limited **POST** carrying the exact validated layout. The signature text includes site, chain, NFT ID, account, expiration and the canonical trap array. The server compares the submitted layout with that signed snapshot, consumes the nonce on any attempt, checks the signature and rechecks current `ownerOf`. The browser snapshots traps before opening the wallet prompt; the old layout-free GET path returns 405. `tests/security-self-review.mjs` signs a disposable challenge, substitutes a valid but different trap and observes HTTP 401; replay also returns 401. Positive ownership signing against a **real NFT** was not tested; a production deployment must enforce its canonical HTTPS host rather than treat an arbitrary request `Host` as independent origin proof. |
| SR-02 **High — persistent NFT arena records** | Anonymous `/api/arena/:id/raid` accepted client-declared wins, loot and scars for NFT arenas. That allowed forged persistent NFT counters/scars, although it did **not** grant CHOG. | Client-reported practice runs may modify **only the open demo pit**. NFT arena raids/scars use the server-run solo/PvP result and scar hooks. Browser-only NFT practice is labeled non-persistent. The regression posts a forged 25-loot NFT win and receives HTTP 403. Demo practice still works in the desktop/mobile smoke test. |
| SR-03 **Medium — API abuse/memory** | Rate limits used arbitrary `X-Forwarded-For` values, and NFT arena signature challenges were not bounded. Repeated requests could evade that limit and grow nonce state. Expensive NFT/RPC GETs were not limited. | Rate keys now use the TCP peer address, **not** untrusted forwarding headers; the rate map and five-minute signature map have capacity/expiration guards. Challenge creation, NFT metadata/owner reads and chain balance reads are limited. A test rotates `X-Forwarded-For` on every request yet reaches HTTP 429, then verifies lookup throttling. **Caveat:** users behind one reverse proxy may share a limit; production needs authenticated proxy configuration and per-account/bot controls, not a blind return to trusting headers. |
| SR-04 **Medium — live-room availability** | WebSocket upgrades accepted browser requests from another origin; a burst of slow asynchronous NFT lookups could pass the 60-room check before any room was inserted. Anonymous idle socket count was not bounded. | Browser `Origin` must match the requested host; simultaneous sockets are capped at 240; pending room creations count toward the 60-room ceiling and are rechecked after the lookup. Cross-origin/same-origin socket checks and a 61-concurrent-create regression pass. **Origin is not authentication:** scripts can omit/forge it, and an IP-based/global cap does not defeat distributed abuse. |
| SR-05 **Medium — draft claim/sponsor hygiene** | The unused wallet helper did not compare proof `chainId`/`vault` with the selected chain/vault, and neither the draft vault nor helper limited proof work to the maximum tree height. A helper accepting an arbitrary gas estimate could prepare a costly sponsored transaction. | The helper rejects mismatched proof domains and estimates above a **500,000-gas per-transaction ceiling** when `allowSponsor` is used. Draft vault and helper reject proofs longer than **six siblings** (40 leaves maximum). Mock-chain tests check oversized on-chain proof rejection, proof-domain mismatches, and that an inflated gas estimate stops **before broadcast**. The cap is a test-helper guard, **not** a production gas-price/budget/rate policy or a production relayer. |

These fixes protect **preview integrity** and draft/test helpers; they do not create real prize eligibility or claimable credit.

## Still open — release blockers, not fixed or signed off

| Severity | Blocker / required decision |
|---|---|
| **Critical — prize legality and rules** | Qualified counsel must review the actual written campaign rules, organizer/player jurisdictions (including Nigeria if accessible), free-entry random token awards, ages/geographies, disclosures, taxes, sanctions and campaign termination. A report that rules are “approved in writing” is not an inspected document or a legal opinion. Self-review cannot substitute for this. |
| **Critical — no real entitlement path** | The hosted game writes only `NON_ELIGIBLE_PREVIEW` box observations and non-redeemable examples; local `LOCAL_TEST_ONLY` claims use isolated mock data. `/api/claims/status` reports `ready:false`, and public proof routes return HTTP 423. There is no audited/deployed/funded vault, signed production eligibility service, or running sponsor. **Never backfill preview balances or local-test proofs into a real campaign.** The real campaign must begin with fresh eligible events after approval. |
| **Critical — fairness and off-chain trust** | A wallet signature is not proof of one human, legal eligibility or an honest run. Scripted solo play, collusive PvP, multi-wallet farming, operator omission of an opening, and incomplete/reordered batches have no reviewed production controls. The local hash-linked journal proves consistency only for events actually recorded and does not withstand an administrator rewriting its database and hash chain together. New production intake/outbox, independent inclusion checkpoints, appeals and anti-farming rules are needed; the preview's five-box daily cap is **not** an approved real rule. |
| **High — vault liveness and close-out** | The Pyth callback may fail permanently, leaving worst-case reserves locked. The draft deliberately has **no owner sweep, refund, unredeemed-proof expiry or close-out path**; none should be invented without approved player/owner rules and an independent contract review. Unused CHOG, outstanding positive credits, unredeemed proofs, callback recovery and campaign end dates must be specified and audited. The current draft **does** permit withdrawal of **any positive credit**, including one 5-CHOG box; keep **no withdrawal minimum**. |
| **High — independent final-system security review** | Independently review final vault/token/oracle addresses and bytecode, callback assumptions and variable fees, ERC-20 behavior, front end and wallet messages, NFT owner checks (including contract wallets), server gameplay/anti-cheat, proof inclusion, sponsor security and operational recovery. Local Ganache tests and this self-review are not independent sign-off. The owner can unpause the draft contract; software alone cannot prove external approval. |
| **High — sponsorship and availability** | `allowSponsor` is a **local wallet helper**, not an authenticated relayer. It does not enforce an independently configured vault allowlist, gas-price/total spend ceilings, per-player limits, approval workflow or incident response. Active rooms are memory-only; a crash loses in-progress rounds. The preview JSON and SQLite observation journal lack a production atomic reward outbox and automatic offsite backup. A deployed proof service, signer/key custody and monitored infrastructure do not exist. |
| **Medium/High — development dependency advisories** | On this date `npm audit --omit=dev --json` reported **0 known production-dependency advisories**, but the **full** `npm audit --json` reported **9 advisories** in the development/test tree: 1 critical, 6 high, 1 moderate, 1 low (including `elliptic` and Ganache/transitives). Do **not** treat a production-only zero as a clean full dependency review. Keep dev tools/ephemeral test keys off a production server, do not use real signing keys in Ganache tests, and review upgrades or replacement of this test harness; blind `npm audit fix --force` suggested a potentially breaking Ganache change and was not applied. Reassess advisories and actual lockfile before any production deployment. |

**Economics remain unapproved:** a read-only mainnet `getFeeV2` query on 17 October returned **1.4 MON per Pyth request**, contrary to a stale 0.4-MON documentation figure. The draft makes one request per **batch** (at 40 leaves, 0.035 MON oracle fee/box at that quote) before commit, redemption, withdrawal and deployment gas. The fee can change. A sponsor paying for every claim with **no withdrawal minimum** needs an explicit budget; no MON balance or sponsor signer was provided.

## Safe wallet separation — plan only, no transactions authorized

1. Keep the reported **1,000 CHOG** in an owner-controlled wallet or multisig until rules and independent reviews are actually verified. The owner independently verifies the real token, chain ID **143**, audited vault bytecode and custody before any explicit wallet-confirmed transfer. No transfer/deployment is requested by this review.
2. Use a **separate, limited-MON sponsor wallet** for public permissionless `redeem`/`withdrawFor` gas. It must not hold the CHOG pool or unrestricted authority to publish prize roots. The draft `commitBatch` is `onlyOwner`; to have the sponsor cover that owner's MON costs without giving away root control, the sponsor would top up the **owner's MON**, and the owner would still inspect and authorize root/fee transactions. A public address alone is not a relayer.
3. Only after approvals, design a new audited campaign pipeline with a signer service that checks published inclusion, recipient and proof domain, an allowlisted audited vault, request authentication, transaction simulation, gas-price and per-tx/total spend caps, replay and farming limits, monitored oracle fulfillment, backing reserves, incident pauses and independent retained backups/checkpoints. No purchase/NFT/CHOG holding requirement and **no withdrawal minimum** should be silently introduced.

**Bottom line:** the review fixed specific preview and draft-helper vulnerabilities, but **it did not make real CHOG claims live or the product launch-ready**. Continue with qualified prize-law review of the supplied rules, independent full-stack security audit of the final implementation, approved oracle recovery/close-out terms and a separate production eligibility/sponsor system before discussing funding or launch.
