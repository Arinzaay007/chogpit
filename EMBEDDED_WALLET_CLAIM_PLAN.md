# CHOGPIT — registered wallet → free NFT claim (design, not live)

**19 October 2026. Decision updated:** the genuine Monad-mainnet CHOGPIT Raider Pass will have a **hard maximum of 40 NFTs**. Players optionally sign up by email; **CHOGPIT triggers a user-controlled, recoverable embedded EVM wallet to be created for them automatically**. They do **not connect an existing wallet or sign a wallet message at registration**. The pass is **not minted at registration**, only if that player deliberately claims it in a separate portal. The project would submit the transaction and pay MON gas. Official minted Chog NFTs remain the owner-built arena deeds. Guests can keep playing, opening *non-redeemable sample* boxes and joining private rooms without registering, getting a wallet or holding any NFT.

**Current reality:** Privy is now the **selected email/wallet provider**. The separate `raider-pass-portal/` bundles the official Privy React SDK for an **email-only login modal**. Privy automatically provisions a user-controlled embedded EVM wallet after successful email OTP; this is **not** its whitelabel `loginWithCode` flow (where `createOnLogin` would not run). The backend verifies Privy’s ES256 identity token and its signed email/DID/embedded-wallet association. **No owner-issued Privy App ID, public verification key or live provider app is configured**, so signup is OFF by default; synthetic tests do not prove a live provider login. Claim and CHOG endpoints stay locked: no Monad pass deployment, project issuer or funded mint service exists. Privy’s own email sender is used for this isolated preview; the older CHOG-candidate mock email flow remains separate. No owner-app recovery/export experience has been verified. The sample badge is off-chain and never converts into a genuine pass/CHOG claim. The undeployed draft hardcodes 40 passes; its 40-mint/41st-rejected test is on a disposable chain, **not Monad mainnet**.

## User control and key safety

- **Do not build a server-custodial wallet:** CHOGPIT must not generate, hold, log, back up or ask users for seeds/private keys. Do not silently park their NFTs in an operator wallet and call it user-owned. Email access alone is neither wallet control nor recovery of an EVM key.
- The chosen embedded-wallet provider must support **Monad chain 143 and EIP-712 signing**, demonstrate actual user control plus a documented recovery/export path across devices, disclose costs/terms and provide a reviewed threat model. A passkey login by itself is **not** an EVM wallet. Do not roll an unreviewed browser-local key generator into the public game.
- Guests must remain wallet-free. Creating a wallet upon verified registration must be an informed user action; it must not be a paid purchase, gas-fee prompt or prerequisite to start a raid.
- **No wallet signing at email sign-up:** the preview trusts only Privy’s ES256-signed identity token for the email, DID and single embedded EVM wallet; it matches these to browser hints without asking for a registration signature. A linked external wallet or bare user-supplied address is rejected. This shifts trust to the actual Privy session and verification key; validate the owner app’s signed `linked_accounts` shape in a live test. The later deliberate NFT claim still needs separate fresh mint consent, and any eventual payout needs new raider-holder proof at transfer. Wallet recovery/binding changes require review. Never collect keys/seeds.

## Supply, fairness and CHOG separation

- `maxSupply = 40` is **an NFT issuance ceiling**. The separate, proposed **40 CHOG-backed box openings** consume at most `40 × 25 = 1,000 CHOG` of verified vault backing if that later campaign launches. **A pass is not an opening, credit or reservation**. The same person could acquire multiple wallets/emails; one lifetime mint per wallet and a 40-token cap are **not one-per-person controls**. With a small supply, a few actors can exhaust it before ordinary players. Choose and publish fair access/rate limits before enabling claim registration or sponsored mints; do not claim email verification prevents farming.
- Passes remain standard transferable ERC-721s in the draft. An email account that once minted but transfers its pass has no automatic CHOG entitlement. A different wallet holding a transferred pass does not become the original opening raider merely by holding it. A future funded program must enforce **box-opening raider + current pass ownership + destination binding** at the transfer, not merely `balanceOf` of an arbitrary supplied wallet. The treatment of pass-unverified backed slots remains undecided.
- The old email candidate is mock-only and the old threshold vault allows CHOG payouts without holder verification. Neither is safe to activate under the new rule. No CHOG or MON has been moved by this prototype. Never send CHOG to the prospective MON sponsor address.

**Selected: Privy (Developer-tier path).** [Privy pricing](https://www.privy.io/pricing) currently lists **free 0–499 monthly active users** and **$299/month for 500–2,499 MAU**; 40 NFTs do **not** limit MAUs or prevent later fees. Do not authorize an upgrade or assume unlimited free use. [Monad’s Privy guide](https://docs.monad.xyz/templates/next-serwist-privy-embedded-wallet) directs owners to disable external wallets and enable automatic EVM wallets. [Privy’s React docs](https://docs.privy.io/basics/react/advanced/automatic-wallet-creation) say `createOnLogin` runs for the **modal**, not whitelabel `loginWithCode`; this preview uses the email-only modal. [Privy’s identity-token docs](https://docs.privy.io/user-management/users/identity-tokens) distinguish the signed user-data token from an access token. Independently check user control, recovery/export, EIP-712 support, current pricing, exact dashboard settings and account availability. No owner Privy app is configured; no monthly-free production rollout is promised.
